- 日付: 2026-10-25 JST。
- 状態: 作業の優先順位と打切り条件を採用。製品要件・数値条件・G1 FAIL は変更しない。
- 起点: PR #5 の `6251ed260e4dfd04ebf23e28d2f22553d9ce3825`。
- 関連: [ADR 0003](0003-dfine-foundation.md)、[ADR 0004](0004-dfine-investigation-checkpoint.md)、[STATUS](../STATUS.md)。

## 点検した理由と結論

ユーザーから「ドツボにはまってないかは確認してね」と指示された。実装者とは別の2担当が、保存済みの数値証拠と製品への進捗を読み取りで点検した。追加推論を行って原因を追う代わりに、次の実験がどの判断を変えるかを見直した。

これまでの調査には、失われた作業の再現性を取り戻し、比較箇所を正しく定義した価値がある。[最新の矩形測定](../verification/2026-10-25-decoder-localization.md)では、同じ ONNX 入力に対する3 MLP の完全一致と3 decoder layer の許容差内の一致を確認した。一方、直近2回の診断追加では、製品機能・G1・未使用実データの品質認定は増えていない。

**「さらに細かく分ける」を自動的な次の作業にすると、数値差の説明が開発の目的になり得る。予定していた decoder 全体の同一入口 replay は保留し、現在の証拠で PR #5 を一区切りにする。** 不一致の発生位置だけが変わり、どの結果でも次の分解を続ける調査は採らない。

## 数値差と品質の扱い

固定した PyTorch 2.6 の[数値精度の説明](https://docs.pytorch.org/docs/2.6/notes/numerical_accuracy.html)は、浮動小数点の演算順序や実装・環境によって、数学的に同じ計算でも bit 単位の一致が保証されないことを説明している。これは一般的な注意であり、今回の差が無害という証明ではない。

現在の G1 は完全な bit 一致ではなく、各要素の `abs(actual-native) <= atol + rtol*abs(native)` を要求している。元の条件は保持する。「FP32 だから仕方ない」「最終 box は近い」「不合格が少数」という理由で FAIL を PASS にしない。同時に、内部テンソルの不一致だけで実用精度の劣化が証明されたとも扱わない。

品質や学習への影響を調査用経路で測定することは、G1 が FAIL でも可能である。調査用モデルを製品 UI・Pages へ公開する許可とは別に扱う。数値契約を見直す場合は、独立した根拠、対象の比較、未使用入力での評価、旧結果の保持を別 ADR で先に定める。観測した最大値へ閾値を合わせない。

## 追加の局所診断を始める条件

開始前に次の4点を短く記録する。

1. 今の証拠で分からない問いと、具体的な修正仮説。
2. 結果が通る場合と通らない場合に、どの実装判断を変えるか。両方が「さらに分解する」だけなら開始しない。
3. 固定入力・比較方法・判定条件と、実行回数の上限。
4. 打切り条件。局所診断の追加は1テーマ・最大1実験、準備・実装・測定・整理を含む実作業90分を初期上限にする。CI待ちを使って調査対象を増やさない。

上限到達、判定不能、再び同じ結論となった場合は、ログを保存して打ち切る。入力・seed・精度・backend の組合せを後から増やしたり、合格するまで続けたりしない。追加調査には新たな判断上の価値を示す。明確な演算・変換不具合が見つかった場合は、その修正と回帰確認を別の小さい作業単位にする。

## 次の検出作業で答える問い

**各 runtime が自分で計算した特徴を使うと、同じ学習レシピの PyTorch に比べ、ブラウザでの学習と学習後の出力が悪化するか。** 次の実装計画は、この影響測定を優先する。現時点では未実施であり、データ・数値条件・step 数をこれから事前固定する。

最初は既存の80クラス・最終 pretrained bbox/class ヘッド・prefix/LQE 固定の範囲で比較する。この試験と同時に独自クラス、全層学習、別モデル、別 backend を追加しない。

- 公開・利用条件を確認した実注釈データを選び、学習・調整と未使用評価を分け、画像・注釈・分割の hash を固定する。合成矩形は回帰用であり、品質評価の代わりにしない。
- PyTorch と実ブラウザで、初期重み・前処理・画像順・ラベル・学習対象・損失・optimizer・step 数・乱数条件をそろえる。それぞれ自身の prefix 特徴で学習する。
- 開始時と事前指定した checkpoint では、ブラウザの特徴と同一重みを PyTorch ヘッドへ渡す短い対照比較も行う。上流から来る差と、ヘッド以降で生じる差を切り分ける。
- matching、VFL/L1/GIoU の内訳、全学習対象の勾配・更新、固定重みの不変、学習前後の logits/boxes と未使用データの検出結果を保存する。query 再整列や参照 matching の強制で主比較を一致させない。
- 学習後の完全 ONNX を別ブラウザセッションと Python CPU で再実行する。
- 評価指標・合格条件・試行数・実行時間の上限を、評価結果を見る前に次の計画へ記載する。既存の同一特徴・2 step 試験をこの実経路の比較の代用にしない。

| 結果 | 次の判断 |
| --- | --- |
| 双方が改善し、事前指定した学習・出力影響の条件内 | 現候補を継続する根拠にする。独自クラスや学習範囲の次段階を検討する。旧 G1 は自動的に変更しない |
| 同一特徴の対照が事前条件外（改善の有無にかかわらず） | ヘッド・損失・更新で生じた差を優先して切り分け、確認した実装不具合を修正する |
| 同一特徴の対照は通るが、実経路の学習・出力影響が事前条件外（双方が改善する場合も含む） | 条件を満たさなかった入力・matching・更新から、上流差の影響を絞る。全演算の自動巡回には戻らない |
| 参照側が改善しない、資源超過、または予算内で判定不能 | 学習範囲・設定・データ適合性を再評価する。runtime の不良やモデル変更の必要性を即断しない |

非有限値・重み破損・同一入力の対照比較の不合格では、その原因と成果物を保存して当該実験を止める。独自クラス・実用品質・全 fine-tuning は、この限定比較だけでは認定しない。既知の過去6入力は未使用入力と呼ばず、失われた生ログを再実行証拠にしない。

## 製品の進捗と PR の区切り

- 検出の診断だけで全開発を止めない。既に動く分類について、未使用実画像での品質と同条件 PyTorch 比較を P1 内の独立した優先作業にする。保存・再開は引き続き残課題として扱う。
- 各作業の報告では、使えるようになった機能、減った重要な不確実性、未達ゲートを区別する。テスト数や調査コードの増加を製品完成度の代用にしない。
- PR #5 の完了条件は、既知の失敗の再現・局所診断・証拠・未解決範囲・次の判断が保存され、回帰確認とレビューが完了したこと。検出器全体の合格まで同じ Draft を延長しない。追加の decoder 診断は本 PR に積まない。
- この記録を含む確認後、PR #5 は調査基盤のチェックポイントとしてユーザーへマージを案内する。マージはユーザーが行う。次の検出影響測定は別 PR に分ける。

ONNX 必須、ブラウザ学習、商用条件、学習済み位置推定を引き継ぐ検出、静的配信のみという要件は維持する。D-FINE や実行系の変更は、学習・品質・資源の比較証拠に基づいて判断する。
